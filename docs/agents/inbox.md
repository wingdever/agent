# inbox 输入队列

## 1 结构

每个 agent 实例持有两个输入队列，均为进程内内存态（`Agent.inbox`，按 sessionId 在注册表中寻址）：

```
inbox = {
  nextTurn: Message[]   // 等当前轮结束后开启下一轮
  nextStep: Message[]   // 当前轮的下一个 step 就交给模型
}
```

一条消息为 `{ id, content, source }`。`id` 由入队方生成，同一队列内唯一。`source` 取值与落库时的消息来源一致。

`nextTurn` 承载「下一次独立输入」：真人发来的新消息、父级对子代理的结算通知、子代理被唤醒时的任务。`nextStep` 承载「当前这轮还没结束就该看到的东西」：树内另一个 agent 的运行中消息、用户对进行中轮次的转向输入。

## 2 入队与唤醒

- `target = "next-turn"` 且目标空闲：入队后立即唤醒一轮。
- `target = "next-turn"` 且目标正在跑：只入队，不唤醒——当前轮结束时会自然领取。
- `target = "next-step"`：只入队。目标正在跑时，当前轮的下一个 step 边界领取；目标空闲时改为进 `nextTurn`（没有进行中的 step 可插）。

入队本身不拒绝忙碌目标，入队的返回值就是最终落入的队列。

唤醒只做一件事：把 `phase` 从 `idle` 置为 `running` 并开始领取输入，不并发开第二轮。

## 3 领取

- **轮次边界**：从 `nextTurn` 领取一条，作为该轮的首条输入。
- **step 边界**：从 `nextStep` 领取全部，按入队顺序追加到本 step 的请求历史。

领取即消费：从队列移除。领取后消息写入 `messages` 表，`role=user`、`source` 取消息自带来源、`surface_seq` 单调递增。回放、压缩、UI 都经这条落库消息看到它，inbox 本身不提供历史。

`nextStep` 领取到的消息是本轮中间插入的 user 消息，与 tool result 交错，因此必须落库，否则回放出来的历史与本次请求前缀不一致。

## 4 一次请求的排列

轮次的首个 step：`[历史] → [本轮 nextTurn 输入] → [运行时上下文快照]`。

后续 step：`[历史] → [本 step 领取的 nextStep 消息]`。轮首的快照已经作为历史的一部分留在前面，本 step 不重新生成快照。

快照只在轮首生成一次，因此轮内请求的尾部只追加领取到的消息，其前的内容都是可命中前缀缓存的稳定历史。

## 5 内存态与丢失

两个队列都不落库。进程退出时未领取的消息丢弃，不暂存、不补发。这是有意的取舍：输入队列是投递通道，不是事实存储。

丢失的后果与恢复路径：

- 普通用户输入丢失：用户重发。
- 树内 `send_message` 丢失：发送方拿到的只是投递回执，不代表对方已处理；需要确认时应以目标会话历史为准。
- 子代理结算通知丢失：子会话本身是持久会话，其末轮 assistant 文本仍在 store 里；恢复入口是从子会话历史重新接入结算，作为显式操作由用户或控制面发起。

## 6 结算通知的投递

子代理一轮结束时产生一条结算通知，走 inbox：

- 父会话正在跑一轮：进父的 `nextStep`，父在下一个 step 就看到结果。
- 父会话空闲：进父的 `nextTurn` 并唤醒一轮。
- 父会话已删除或不存在：丢弃并记录告警，不暂存。

结算通知领取后以 `source=subagent-settle` 落库，是父会话里的一条普通 user 消息，不带 `tool_call_id`。

## 7 queue 与 steer

两种输入模式的区别只在目标队列：

- **queue**：进 `nextTurn`，等当前轮结束。真人通过 `chat.send` 发消息时，若目标正在跑一轮，默认走 queue，回执带 `queued: true`。
- **steer**：进 `nextStep`，当前轮的下一个 step 就交给模型。用于纠正跑偏、追加约束而不打断当前工作。

两种模式都不拒绝忙碌目标：忙碌只改变消息去的队列，不产生错误。

## 8 wait_agent

`wait_agent` 让调用方在下一个 step 边界等待输入出现，不消费输入：

- 等待条件是本 agent 的 `nextStep` 出现此前未报告过的消息。
- 有新输入立即返回 `{ timedOut: false }`；超时返回 `{ timedOut: true }`，`timeout_ms` 取值 10000–3600000，默认 30000。
- 同一个工具调用内已报告过的消息不重复触发等待结束——它们要等本 step 结束才会真正进入请求，重复触发只会让等待空转。
- 调用方 agent 被销毁或插件卸载时等待以错误结束，不悬挂。
